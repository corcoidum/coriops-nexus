## 보고서 버전 제안의 상세 규칙

- 의뢰의 전체 검체 목록을 발송 시 고정한다. `BOTH`도 [가정] 의뢰 1건이며 검체 부위로 구분한다.
- 수탁기관 보고서 1개가 여러 검체를 포함하거나, 검체별로 서로 다른 보고서가 올 수 있다. `ReportSpecimen`은 양쪽 모두 표현한다.
- `logical_report_key`는 한 보고서 계열을 식별한다. 정정본은 동일 의뢰·동일 계열, 직전 버전의 `supersedes_id`와 사유를 가져야 하며 원본을 덮어쓰지 않는다. 같은 직전 버전에 두 갈래 정정은 금지한다.
- 유효 결과 집합은 계열별 최신 버전의 검체 coverage 합집합이다. 모든 발송 검체가 포함되어야 `RESULT_RECEIVED`다. 미도착·검체 부적합·재채취를 정상 수신으로 임의 간주하지 않는다.
- 정정본은 그 계열의 coverage 전체를 명시한다. 확인 완료 뒤 coverage 감소는 접수 보류 후 원장 정정 절차로 `SHIPPED`까지 되돌려 처리한다. 정상 수신인 척 종결하지 않는다.
- 원장 확인은 당시 유효한 **모든** 버전 UUID를 `ReviewReport`와 `report_set_hash`로 고정한다. 새 보고서 접수와 review가 경합하면 의뢰 잠금 후 최신 hash 재검증한다.
- 정정본 접수는 SYSTEM의 임상 판단이 아니다. 수신 권한자가 기록하고, 새 WorkCycle로 재확인 Task를 만든다. 임상 분류·F/U 날짜는 복사해 확정하지 않는다.
- 기존 F/U 계획은 `RECONFIRM_REQUIRED`로 표시하고 원래 날짜는 유지한다. 기존 임박·지연 R07·R08도 원장 확인 전 숨기지 않는다. 재확인 시 원장이 유지·수정·취소하며 사유를 남긴다.
- 부분 결과의 조기 원장 전달은 아직 승인되지 않았다(Q02). 따라서 이 문서는 구현 준비가 끝났다고 선언하지 않는다.

## 과도한 선행 구현을 막는 경계

WorkCycle은 재작업 구분자, SubjectReference는 polymorphic FK 보완, 보고서 연결 테이블은 실제 검체 coverage다. 범용 프로세스 디자이너, 이벤트 버스, KG, AI Agent 실행기는 추가하지 않는다. 커널 Engine은 등록된 객체·guard만 호출하며 모듈을 import하지 않는다.

## 추가 발견 — P14와 지정 파서의 요구 해석 충돌

**확정사항:** 원본 디스크 미저장·ignore 값 DB/로그/preview 미저장은 요구사항이다. **관찰:** [openpyxl 공식 reader 소스](https://openpyxl.readthedocs.io/en/stable/_modules/openpyxl/reader/excel.html)는 sharedStrings를 먼저 읽는다. **제안:** 앱의 선택·매핑·저장 금지와 파서 내부 읽기를 구분하고 허용 필드 전용 입력을 검토한다. **사용자 확인 필요:** Q16. 파서 내부에서도 무시 값 읽기 0을 요구한다면 현재 openpyxl 기본 읽기 경로로 충족한다고 말할 수 없다. 요구를 임의로 완화하지 않고 구현 전에 멈춘다.
