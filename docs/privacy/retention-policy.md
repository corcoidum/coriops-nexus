# 보유·파기 정책 초안

**법률 자문이 아닌 초안, 원장 결재·확인 필요.** Q06 답변 전 운영 파기·실데이터 사용을 허용하지 않는다. [개인정보 보호법 제21조](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900078981)의 불필요 정보 파기 원칙을 참고하되 개별 보유 근거는 원장이 확인한다.

## 승인된 파기 실행의 설계

1. 서비스가 정책 버전·Clock으로 후보와 의존관계를 계산한다. 활성 의뢰·F/U·법적 보유 보류가 있으면 후보에서 제외하며 무기한 방치 대신 사유·재검토일을 관리한다.
2. 책임자가 대상 UUID 목록·건수·기간·의존성 요약을 검토하고 동일 manifest hash에 승인한다. 후보가 달라지면 승인을 다시 받아야 한다. 환자 상태 PURGE_PENDING은 대기 표시이며 최종 삭제를 대신하지 않는다.
3. 실행 시 대상을 잠그고 보유기간·새 F/U·정정·권한을 재검증한다. 경쟁 변경이 있으면 실패시키고 목록 재작성한다.
4. backup보다 최신인 별도 로컬 파기 ledger에 승인 manifest를 내구성 있게 보관한다. 임상값·직접식별정보는 넣지 않는다. 삭제 트랜잭션과 ledger 확정 상태를 대조하고 중간 장애를 재시도한다.
5. 모듈 등록 순서로 관련 Task/Notification/Plan/Cycle/검체 연결/보고서/Review/의뢰/registry를 삭제한다. Patient는 다른 보유 대상이 없을 때만 삭제한다. 별도 보유가 승인된 로그를 cascade하지 않는다.
6. 같은 트랜잭션으로 파기 건수·Actor·정책 버전·manifest hash·성공시각을 남긴다. 원래 chart_no·이름을 파기 증명으로 복제하지 않는다. 실패는 rollback하고 오류 코드만 기록한다.
7. 백업·WAL·snapshot·장치 잔존 점검을 끝낸 후 최종 운영 파기 완료를 확인한다. SQL DELETE 성공 시각과 전체 매체 파기 확인 시각을 혼동하지 않는다.

## 복원·로그 만료

백업 복원은 app과 LAN을 끊은 격리 DB에서 수행한다. 가장 최근 파기 ledger를 먼저 주입해 해당 UUID를 재파기하고 검증한 뒤 접속을 연다. ledger가 없거나 백업이 30일 초과면 자동 운영 복원을 금지하고 책임자에게 보고한다. 파기된 정보가 복원되는 것을 방지하는 운영 절차이지 백업 잔존의 적법성 승인을 대신하지 않는다.

로그의 기간 segment를 지울 때도 만료 정책·승인·기존 독립 checkpoint를 보존한다. 검증기는 승인된 segment 만료와 임의 중간 삭제를 구별해야 한다. app은 삭제 권한이 없다. checkpoint·ledger 자체의 식별 가능성과 보유·파기도 Q06에 포함한다.

PostgreSQL MVCC·WAL·SSD·snapshot의 물리 잔존 제거는 row DELETE만으로 증명할 수 없다. 암호화 볼륨, 백업 순환, 장치 폐기 방법과 원장/전문가 확인을 합쳐 Q06에서 방법을 확정한다. 요구를 충족할 방법이 확정되지 않으면 Phase 5 개인정보 완료 처리를 중단한다.
